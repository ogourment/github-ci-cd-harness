
## Lessons learned

Concise dated entries, most recent first. Format: what failed or was discovered → the fix → **Consider:** what to do differently next time.

- `2026-07-19` Every pipeline since #1399597 failed on a hidden `pages:deploy` `GenericCommitStatus` (invisible via the REST Jobs API, only visible via GraphQL/commit statuses) with the generic error "include a `public/` folder ... or specify `publish`", even though `acceptance_pages` always succeeded and its uploaded artifact genuinely contained `public/index.html`. Neither a trailing-slash fix to `artifacts.paths` nor renaming the job to the legacy `pages` convention changed anything. The real cause: this project had never had a first successful Pages deployment (confirmed via framagit's own `/pages/new` "get started" wizard, only shown for zero-deployment projects, and via `pages_access_level` being `private` instead of `public` like sibling projects). A throwaway job matching GitLab's wizard skeleton exactly — self-contained script (no `needs`), `rules: if: $CI_COMMIT_REF_NAME == $CI_DEFAULT_BRANCH` — bootstrapped a deployment successfully on the first try. **Consider:** on a brand-new GitLab project, a Pages job that depends on another job's artifacts via `needs:` and/or runs unconditionally on every ref (including tag pipelines) may never get past the very first deploy attempt; bootstrap with a minimal self-contained job restricted to the default branch first, then verify the real job that consumes upstream artifacts separately — don't assume the first deployment "unblocks" a different job name once and for all.
